# Source information in images

An image can say which Lean declaration made it. PILean writes this into SVG, PNG, APNG and GIF
files and reads it back; `lake exe pilean-info FILE` prints it. The code is in
`PILean/Trust/Provenance.lean`; the SHA-256 used for fingerprints is `PILean/Trust/Sha256.lean`.
The sections from "Renderable figures" on say how a build produces the files with their source
record, a fingerprint and a manifest, and how to check them. What a picture's theorems say about
the Lean object it shows, and what stays tested or trusted, is on
[`PROOFS.md`](PROOFS.md) ("What an image proves").

## The record

`PILean.Trust.Source` has these fields; the keys below are used in every format.

| Key | Meaning | Required |
|---|---|---|
| `module` | the Lean module of the declaration | yes |
| `decl` | the declaration's name | yes |
| `file` | the file, relative to the repository | yes |
| `line`, `column` | where the declaration starts (decimal numbers, at most nine digits) | yes |
| `repo` | the repository's URL | no |
| `commit` | the commit the image was built from | no |
| `version` | the version of PILean (`PILean.version`) | yes |
| `fingerprint` | 64 lowercase hexadecimal digits (a SHA-256) | no |

A record can be written only if every value is at most 4096 bytes of UTF-8 and has only
characters XML 1.0 can carry (so no NUL and no other control character except tab, line feed and
carriage return), and a fingerprint has the form above (`Source.validate`).

## Writing

The writers of images are unchanged: an image without a source is byte for byte what it was
(the gallery in `examples/` is compared with its files on every test run). The source is added to
a finished file:

* `withSourceSvg (svg : String) (s : Source)`, `withSourcePng`, `withSourceGif`, or
  `withSource`, which finds the format by the file's signature. Each returns
  `Except String ByteArray` (the SVG one a `String`), and fails if the file already has a
  source.
* For an SVG built from nodes, `Source.svgNodes` gives the three elements to put first among the
  children of `Svg.document`.

### SVG

Three elements, the first children of the root `<svg>`:

```xml
<title>Module.decl</title>
<desc>Generated by Module.decl in path/File.lean:59 with PILean 0.1.0</desc>
<metadata>
  <pilean:source xmlns:pilean="https://github.com/eric-vergo/PILean/ns/source/1"
      module=".." decl=".." file=".." line=".." column=".." repo=".." commit=".."
      version=".." fingerprint=".."/>
</metadata>
```

Absent optional fields are left out. Values are escaped with the writer's attribute escaping
(`&amp; &lt; &gt; &quot; &#39;`, tab, line feed and carriage return as character references).

### PNG and APNG

One `iTXt` chunk per field, uncompressed, UTF-8, with the keyword `PILean:` followed by the key
(`PILean:module`, `PILean:decl`, `PILean:file`, `PILean:line`, `PILean:column`, `PILean:repo`,
`PILean:commit`, `PILean:version`, `PILean:fingerprint`), directly after `IHDR`, so before `IDAT`
and, in an APNG, before `acTL` and every `fcTL`. The chunks have correct CRCs. The pixels and the
frames are not touched.

### GIF

One comment extension (`0x21 0xFE`) directly after the global colour table, so before the first
image and before any application extension. Its text is UTF-8 lines: `PILean source 1`, then
`key=value` for each field (the value is everything after the first `=`), each line ended by a line
feed, in sub-blocks of at most 255 bytes. A GIF comment is line based, so a value with a line
feed or a carriage return is refused (SVG and PNG carry them). The file must be a GIF89a file.

## Reading

`Source.read? : ByteArray → Except String Source` finds the format by signature (PNG; `GIF8`;
otherwise UTF-8 text with an `<svg` tag) and treats everything as untrusted:

* The input must be at most 64 MiB (`maxInput`); each value at most 4096 bytes (`maxField`).
* Each key at most once (a repeat is an error); a value with a character XML 1.0 cannot carry is
  an error; unknown keys are ignored; the required keys
  must be there; `line` and `column` must be numbers; a fingerprint must have the form above.
* Nothing is executed or followed. A `repo` value is returned as text.
* SVG: a small bounded scanner over the bytes skips comments, processing instructions and CDATA
  sections, and reads only the attributes of the one `pilean:source` element, which must declare
  the namespace above (a second element, an unknown entity, a `<` in a value or a character
  reference to a character XML cannot carry is an error). The five XML entities and numeric
  character references are unescaped. There is no general XML parser.
* PNG and APNG: the chunks before the first `IDAT` are walked; the CRC of a source chunk must be
  right and it must be uncompressed. The image is not decoded.
* GIF: the extensions before the first image are walked; the comment that starts with
  `PILean source 1` is read; a larger one than 64 KiB, a second such comment or a carriage
  return in it is an error.
* What the readers accept is what the writers write: a value with a character XML cannot carry
  (NUL, say) is refused in every format, as the writers refuse it. One difference is kept on
  purpose: the APNG reader treats a frame delay with denominator 0 as a denominator of 100, as
  the APNG specification says; the writer never writes one.

### Links

`safeLink? : String → Option String` answers a URL only if it starts with `http://` or
`https://` (lowercase), has something after that, is at most 4096 bytes and has only printable
ASCII without `"`, `'`, `` ` ``, `<`, `>`, `\` and white space. Anything else (`javascript:`,
`data:`, `file:`, a non-ASCII character) gives `none`; a program that shows a link should use
only what this returns.

`escapeControl` writes control characters and the backslash of a string as escapes (`\n`, `\t`,
`\u{1b}`), for showing untrusted text on one line.

### Inert SVG

`Svg.isInert : String → Bool` answers whether an SVG document can be shown in a web page without
running script, loading anything from outside the document, or carrying event handlers;
`Svg.inertProblem?` gives the first reason it is not. It is a small bounded scan over the text,
not an XML parser, and it is strict: it accepts the SVG PILean writes (figures, graphs,
animations, and files with a source record) and refuses anything else that could be active.

* A document above 64 MiB is refused without being read; the work is linear in its size.
* The only markup is one `<?xml ...?>` declaration at the very start (with no `<` or `>`
  inside it), comments (without `--` inside, not starting with `>` or `->` and not ending with
  `-`, so that an HTML parser and an XML parser end them at the same place), and elements
  from a fixed list: `svg g path rect circle ellipse line polyline polygon text tspan title desc
  metadata pilean:source defs clipPath linearGradient radialGradient stop animate
  animateTransform set style`. `script`, `foreignObject`, `image`, `use`, `a`, any unknown
  element, a document type, an entity declaration, a CDATA section, any other processing
  instruction, and a tag or comment that is not closed are refused.
* Attribute names have ASCII letters, digits and `- _ : .` only, and values are quoted. Names
  starting with `on` (in any letter case) are refused, as are `style` attributes and `xml:base`.
  `href`, `xlink:href` and any name ending in `:href` are accepted only with a value that starts
  with `#`. A `url(` in a value must be followed by `#`. `javascript:` and `data:` are refused
  in any value, also with white space inside, as are the CSS image functions `image(`,
  `image-set(`, `cross-fade(` and `src(`. A backslash in a value is refused. An animation
  (`animate`, `set`, `animateTransform`) of `href`, a name ending in `:href`, or a name starting
  with `on` is refused (`attributeName` is recognised in any letter case, as an HTML parser
  reads it).
* Values are decoded before they are checked: the five XML entities and numeric character
  references are decoded, any other `&name;` is refused, so a reference cannot hide a word.
* The text of a `style` element may not contain `@import`, `@font-face`, `url(` that is not
  followed by `#`, `image(`, `image-set(`, `cross-fade(`, `src(`, `expression`, `binding`,
  `behavior`, `javascript:`, a backslash, a character reference, or any `<` other than the
  closing `</style>`. Text in other elements is not examined; a raw `<` always starts a tag.
* Elements are closed and nested properly, at most 256 deep; there is exactly one root element,
  `svg`, and nothing but white space and comments after it.

An SVG that passes can be placed in a page as an image or inline; the check says nothing about
whether the figure is the right one (see the fingerprint for that). Placed inline, the rules of
its `style` element apply to the whole page, as those of any inline SVG do: they cannot run
script or load anything, but they can restyle what is around the picture. The check is tested
against hand-written hostile documents; it is not proved, and no browser is part of the tests of
the core.

## `pilean-info`

```
lake exe pilean-info FILE
```

prints one `key: value` line per field, in the order of the table above, values with control
characters escaped. Exit status 0 on success; 1, with a message on standard error, if the file
cannot be read, is larger than 64 MiB, or has no valid source information; 2 on a wrong command
line. The function behind it is `PILean.Trust.infoLines`.

## Renderable figures

`PILean/Trust/Figure.lean`. A type with an instance of `ToOutputs` can be rendered to files:
`ToOutputs.outputs : α → Array Output`, each `Output` with a file-name suffix (`name`: `""`,
`"-dark"`, `"-poster"`), a `Format` (`svg`, `png`, `apng`, `gif`), the bytes (a function of
`Unit`, so nothing is computed before it is called; it can fail with a message) and `spec`, the
canonical encoding of what is drawn.

| Type | Outputs |
|---|---|
| `Plot.Figure` | SVG; PNG |
| `Graph` (default layered layout, light style, scale 1), or `GraphFigure` (graph, layout options, style, PNG scale) | SVG; PNG |
| `Animation` | animated SVG; APNG (file extension `png`); GIF; poster frame (PNG, suffix `-poster`) |

### The specification encoding

The specification of an output is the SVG document that PILean's deterministic writer
(`Svg.render`) makes from the figure's drawing, as UTF-8, before any source information is added:

* SVG outputs: the SVG document of the output itself, with text as `<text>` (as shapes when the
  text engine's strings are not plain text, such as LeAnTeX's).
* PNG outputs of a figure or a graph: the SVG document with text drawn as shapes, which is the
  drawing the PNG is rasterised from (the rasteriser itself is not part of the specification; it
  is covered by the renderer's identity, see "The fingerprint").
* An animation's APNG and GIF: the animated SVG document, which holds every frame; the poster:
  the SVG document of the poster frame.

The specification covers what is drawn: the sampled values of a function (the points the figure
takes), data, colours, sizes, text and layout. It does not cover the function's code, nor
anything that does not change the drawing. The declaration's source text is covered separately,
by the source hash.

## The attribute `figure` and `figures%`

`PILean/Trust/Attr.lean` (the only part of PILean that imports `Lean`; the library proper does
not). `@[figure]` on a definition whose type has a `ToOutputs` instance (it is an error
otherwise, and for a private declaration) records in an environment extension, which is exported
with the module:

* the module, the declaration's name, and the file (the module's name with `/` for `.` and
  `.lean`: `PILeanTest/Examples.lean`; never an absolute path);
* the line (from 1) and column where the declaration starts, taken from the range Lean stores for
  it: the start of its doc comment when it has one;
* the SHA-256 (hexadecimal) of the declaration's source text, the text of that range, taken from
  the file being elaborated.

Lean stores the range only after the attributes are applied, so the attribute adds a command
elaborator for declarations and `attribute` commands that mention `figure`, which elaborates the
command as usual and then records its figures.

The term `figures%` becomes, where it is used, an `Array FigureEntry`: one entry for every
registered declaration of the environment (imported modules included, and the declarations above
it in the same module), sorted by module and then declaration name, each holding the recorded
data and `fun _ => ToOutputs.outputs decl`.

The command `figure_proves fig thm` links a theorem to a registered figure. It is an error, so
the module does not build, unless `thm` is a theorem, depends on no `sorry` and on no axiom other
than `propext`, `Classical.choice` and `Quot.sound`, and its statement names the figure itself.
The links are kept in an environment extension (`figureTheorems`).

The rule, exactly (`statementNamesFigure`, with `ruleStatement`):

1. The statement of `thm` is taken as Lean elaborates it and reduced, everywhere in the term and
   until nothing is left to reduce, by three steps and no others: a `let` or `have` is replaced
   by its body with the value put for the variable; `letFun v f` (the form `have` took in
   earlier versions of Lean) becomes `f v`; an application of a `fun` to arguments is
   beta-reduced. A declared statement has no metavariables, so none are instantiated.
   Eta-reduction is not applied: it removes a binder and a variable, never a constant, so it
   could not change the outcome. A statement whose reduction runs past Lean's limits
   (heartbeats, recursion depth) is refused with Lean's error.
2. The constant `fig` must occur in the result.

Where `thm` is declared is not part of the rule. It is usually the figure's module. In the
Mathlib package it is a module that imports the figure's: the figure's module imports nothing
from Mathlib, so that the program that draws it does not contain Mathlib, and the theorem needs
Mathlib.

What this means:

* A field of the figure is a projection applied to it, so a statement about `fig.panels`,
  `fig.edges`, `fig.nodes` or `fig.frameSeq` names the figure. The usual shape begins with an
  equation that says what the figure holds, `fig.panels.map (·.series) = #[#[s₁, s₂]]` or
  `fig = builder data`, and goes on about `s₁` and `s₂`, or about `data`.
* No definition is unfolded. A statement about a definition the figure is built from (a series, a
  data list, a relation), or about a term that happens to equal the figure, does not name it and
  is refused: the figure could be changed and leave such a statement true.
* A name that occurs only in the value of a `let` the statement does not use, or only as the
  argument of a `fun` that discards it (`(fun _ => P) fig`, also when the `fun` is passed
  through other `fun`s first), does not count: the reduction removes it.
* The reduction stops at definitions, so a name that a definition would discard still counts.
  These are accepted although the figure plays no part in what they say, and the rule does not
  try to see through them: a `match` on the figure (`match fig with | _ => P`), a projection of
  a structure or pair built around it (`(fig, P).2`), a definition that ignores an argument or
  passes a `fun` on (`Function.const _ P fig`, `id (fun _ => P) fig`, or one of the author's
  own), a recursor whose unused case holds the figure (`Nat.rec P (fun _ _ => fig = fig) 0`),
  and an `if` whose condition settles the branch.
* The rule is about names; it does not judge what the statement says. A statement that names
  the figure and says nothing of substance about it passes: `fig = fig`, the figure in a
  hypothesis that is never used or in a branch that is never taken, a property that holds of
  every figure, and the shapes of the previous item. What the theorem says is for its reader to
  judge (`docs/PROOFS.md`).

A link is a pointer from a picture to a statement to read, not a certificate that the picture is
correct.

## The fingerprint

`PILean/Trust/Fingerprint.lean`. `fingerprint spec src` is the lowercase hexadecimal SHA-256 of
this byte string:

1. the header `PILean fingerprint 2` and a line feed;
2. nine fields in this order: module, declaration, file, line, column, library version
   (`PILean.version`), renderer (`rendererWith` of the output's text engine), source-text hash,
   specification;
3. each field as its length in bytes (a 64-bit unsigned number, big-endian) followed by its
   bytes; the text fields are UTF-8, the line and the column are decimal digits, the source-text
   hash is its 64 hexadecimal digits.

The renderer, `PILean.Trust.rendererId` (`PILean/Trust/Renderer.lean`), is the SHA-256 of the
Lean toolchain's version and of the source files of every library module that turns a figure into
bytes (the plots, graphs and animations, the SVG writer, the rasteriser, the lettering, the PNG,
APNG and GIF writers, the source records: the modules `Renderer.lean` imports, listed in
`rendererSources`). It is computed from the files' text as it was when the library was compiled
(`include_str`), so nobody has to remember to change it: any change to that code changes every fingerprint, even a
change to a comment, and a change to the rasteriser that leaves the SVG specification alone
still changes the fingerprints of the PNG files. The tests check that the list is exactly the
modules `Renderer.lean` imports and that each text is the file's current content.

An output drawn with a text engine other than the built-in lettering records that engine's
identity (`Output.textEngine`, from `TextEngine.id`), and its renderer field is
`rendererWith id`: the SHA-256 of `rendererId`, a line feed and the identity (for the lettering,
whose code `rendererId` already covers, it is `rendererId` itself). The LeAnTeX engine's identity
names the LeAnTeX commit and the SHA-256 of every font file it reads (`leantex/README.md`), so
the fingerprint changes with either.

The file's `Source` record carries this fingerprint, so changing the specification, the source
text, the position, the library version or the renderer changes it. The repository and the commit are not part
of it (the same figure built at two commits has the same fingerprint if neither its drawing nor
its declaration changed, apart from the line). Output formats of one animation share one
fingerprint, because they share the specification; the SHA-256 of each file is in the manifest.

## `pilean-build`

A project's driver is three lines:

```lean
import MyFigures
import PILean.Trust.Build
def main (args : List String) : IO UInt32 := PILean.Trust.buildMain figures% args
```

(with `lean_exe` in the project's lakefile). PILean's own driver is `lake exe pilean-build`; it
renders the gallery figures that carry `@[figure]`.

```
pilean-build [--out DIR] [--repo URL] [--commit SHA] [--check]
```

* Without `--check`, every output of every entry is rendered, the source record (with the
  fingerprint, and `--repo` and `--commit` if given) is written into it, and the file is written
  to `DIR/<module with / for .>/<declaration without the module prefix><suffix>.<extension>`
  (`--out` defaults to `figures`), then `DIR/manifest.json`. The output is deterministic: the
  same entries, options and library give the same bytes. Nothing is written if any figure fails
  to render. File names have only `[A-Za-z0-9._-]` (every other character becomes `_`); an empty
  component, `.` or `..` in a path is refused, so nothing is written outside `DIR`.
* `--repo` must be an `http` or `https` link (`safeLink?`), `--commit` 4 to 64 lowercase
  hexadecimal digits.
* With `--check`, the output is rendered in memory and compared byte for byte with `DIR` (give the
  same `--repo` and `--commit` as the build). It prints `stale: PATH` (different bytes, the manifest
  included), `missing: PATH`, and `extra: PATH` (a file under `DIR` that is neither in the manifest
  nor the manifest itself), and `ok: N files match` if all is well. The folder is listed to at most
  32 levels of directories and 100,000 entries (directories count, empty ones included); a folder
  beyond either bound is not listed partly: it gets the line `cannot check: REASON` and fails.
* Exit status 0 on success, 1 if a file is stale, missing or extra, the folder cannot be listed
  completely or a figure cannot be rendered, 2 on a wrong command line.
* Bounds: at most 4096 figures and 65,536 files (the most a manifest may list), each file at
  most 64 MiB with its source record in (the most the source reader of `pilean-verify` reads),
  checked on the finished file; a file whose bytes are not of its output's format (an `apng`
  output must have an `acTL` chunk before its image data, a `png` output none) is refused. So
  every file a build writes is one `pilean-verify` can check.

### The manifest

`DIR/manifest.json` is one JSON object, `{"format":"pilean-manifest-1","files":[ ... ]}`, with one
line for each output, sorted by `path`, every object with the keys in this order:

| Key | Meaning |
|---|---|
| `path` | the file below `DIR`, `/` as separator |
| `format` | `svg`, `png`, `apng` or `gif` |
| `bytes` | the size of the file |
| `sha256` | the SHA-256 of the file's bytes |
| `fingerprint` | the fingerprint recorded in the file |
| `module`, `decl`, `file`, `line`, `column`, `version` | the source record |
| `repo`, `commit` | only if the build was given them |

Strings are escaped as in JSON (`\"`, `\\`, `\n`, `\r`, `\t`, `\u00XX` for other control
characters).

## `pilean-verify`

```
lake exe pilean-verify DIR
```

resolves `DIR` once and reads `DIR/manifest.json` as untrusted input: a regular file (not a symbolic
link, not a FIFO or device; checked before it is opened), at most 16 MiB, read by a small bounded
JSON reader (`PILean/Trust/Json.lean`: nesting at most 8, strings at most 64 KiB, integers of at
most 15 digits only, no repeated key, nothing after the value). The manifest is rejected as a whole,
before any file is touched, if a path is empty, longer than 1024 bytes, absolute, has `..` or `.` or
an empty component, a backslash, a colon or any character outside `[A-Za-z0-9._/-]`, if a path is
listed twice, a format is unknown or a hash is not 64 lowercase hexadecimal digits. The folder is
then listed, to at most 32 levels of directories and 100,000 entries (directories count, empty ones
included); a folder beyond either bound is an error (exit status 1, a message, no line about any
file), never a partial listing. Then each listed file gets one line, and after them each file that
is not listed:

| Line | Meaning |
|---|---|
| `ok: PATH` | a regular file of the listed size and SHA-256 and of the listed format, whose source record agrees with the manifest (module, declaration, file, line, column, version, repository, commit and fingerprint) |
| `missing: PATH` | no file has that path, spelled exactly so (on a file system that ignores case, a file found only under another spelling is `missing`, and listed as `extra` under its own) |
| `changed: PATH` | another size or hash |
| `format differs: PATH` | the bytes are not of the listed format (`svg`, `png`, `apng` with an `acTL` chunk before the image data, `gif`) |
| `not a regular file: PATH` | the file, or a directory on its way below `DIR`, is a symbolic link, a directory, a FIFO or a device (nothing is followed or opened) |
| `source differs: PATH` | the source record in the file differs from the manifest |
| `no source: PATH` | the file has no readable source record |
| `extra: PATH` | a file below `DIR` that the manifest does not list (other than the manifest; a symbolic link counts as a file and is not followed) |

Every path and message printed comes from the folder and goes through `escapeControl`, so no
line can be forged or hidden by the manifest. Exit status 0 only if every line is `ok`; 1
otherwise, or if the manifest is missing or invalid; 2
on a wrong command line. `pilean-verify` does not render anything: it checks that the directory
is what its manifest says. `pilean-build --check` checks that it is what the build produces now.

### What the answers establish

* `pilean-info` prints what a file says about itself. A source record is written by whoever
  wrote the file; nothing is signed, so the record alone establishes nothing.
* `pilean-verify` exiting 0 establishes that the directory and its manifest agree: every listed file
  is there under exactly its listed name, with the listed size, SHA-256 and format, and carries the
  listed source record, and there is no other file (a folder too deep or too large to list
  completely is an error, not a pass; directories that hold no file are not compared). It does not
  establish where either came from. Someone who can write both the files and the manifest can make a
  directory that passes, with any source record; the fingerprint is compared with the manifest's,
  not recomputed.
* `pilean-build --check` exiting 0 establishes that the directory holds, byte for byte, what
  the driver that was run renders now from the declarations compiled into it, and nothing else.
  That ties the files to the Lean source to the extent that the driver was built from that
  source by a toolchain you trust, on the checkout you mean. It is the only one of the three
  that looks at the Lean declarations.
* None of them says that a picture is correct: the fingerprint identifies a drawing and its
  declaration, and the theorems (`docs/PROOFS.md`) are about the Lean object, not the pixels.
* The file checks are made with `lstat` before each open; a folder that another process changes
  during the check is outside what they defend against (`PILean/Trust/Files.lean`).

## Use in CI

Figures are never committed by hand. Either of two set-ups:

1. **Build into the site.** CI runs the project's build driver and the site uses the folder:
   `lake exe my-figures --out site/figures --repo URL --commit "$COMMIT"`. Nothing under
   `site/figures` is in version control.
2. **Keep them committed and prove them.** The folder is in version control, written by
   the driver only, and CI runs `--check` with the same `--repo` and `--commit` (or none, if
   the committed files were built without), which fails when a committed file is not what the
   build produces (edited by hand, outdated, missing, or left over).

A workflow as plain shell steps:

```sh
lake build
lake exe my-figures --out site/figures --repo "$REPO_URL" --commit "$(git rev-parse HEAD)"
lake exe pilean-verify site/figures        # the folder agrees with its manifest
# keeping the folder in version control instead:
lake exe my-figures --out figures --check   # fails on any stale, missing or extra file
```

A change to a figure's declaration changes its source hash and so its fingerprint, and a change to
a sampled value or to the drawing changes the specification; either way `--check` reports the files
as stale until the build writes them again.
