# Source information in images

An image can say which Lean declaration made it. PILean writes this into SVG, PNG, APNG, GIF and
PDF files and reads it back; `lake exe pilean-info FILE` prints it. The code is in
`PILean/Trust/Provenance.lean`; the SHA-256 used for fingerprints is `PILean/Trust/Sha256.lean`.
The sections from "Renderable figures" on say how a build produces the files with their source
record, a fingerprint and a manifest, and how to check them. What a picture's theorems say about
the Lean object it shows, and what stays tested or trusted, is on
[`PROOFS.md`](PROOFS.md) ("What an image proves").

## The record

`PILean.Trust.Source` has these fields; the keys below are used in every format.

| Key | Meaning | Required |
|---|---|---|
| `module` | the Lean module of the declaration | yes |
| `decl` | the declaration's name | yes |
| `file` | the file, relative to the repository | yes |
| `line`, `column` | where the declaration starts (decimal numbers, at most nine digits) | yes |
| `repo` | the repository's URL | no |
| `commit` | the commit the image was built from | no |
| `version` | the version of PILean (`PILean.version`) | yes |
| `fingerprint` | 64 lowercase hexadecimal digits (a SHA-256) | no |
| `standing` | `linked` or `illustration`: the figure's standing as the build recorded it ("Standing" below; `proved` reads as `linked`) | no |
| `motion` | for a file of a motion, its record as one value: `keys=N;cycle=C;captions=N;checks=L;unchecked=yes|no`, with the cycle in seconds as `n` or `n/d` in lowest terms (at most 18 digits each) and the level `fail`, `warn` or `ignore` (`MotionSummary.text`; "Motions") | no |
| `theorems` | for a linked figure, the theorems linked to it, by full name, as a list: `[`, the names separated by `,`, `]`, each name with `%`, `,`, `[`, `]`, the backslash and the control characters written `%XX` (two uppercase hexadecimal digits), such as `[A.b,C.«d e»]` (`theoremsText`); a value that does not begin with `[` is read in the earlier form, names separated by single spaces, and so is the earlier key `proves` | with `standing` `linked` only |

A record can be written only if every value is at most 4096 bytes of UTF-8 and has only
characters XML 1.0 can carry (so no NUL and no other control character except tab, line feed and
carriage return), a fingerprint has the form above, and the standing is well formed: none,
`illustration` without `theorems`, or `linked` with a non-empty list of distinct, non-empty names
(`Source.validate`, `standingOk`; the readers refuse anything else, after reading `proved` as
`linked` and `proves` as `theorems`, and refuse a record with both `theorems` and `proves`). A
name may hold any character a record can carry, a space or a quote included (Lean writes a name
whose component needs it between `«` and `»`); the list's escapes make every list of names one
text and read it back exactly, and refuse an escape that is malformed or not needed and a special
character written as it is. The list has no backslash, which an inert SVG may not carry in an
attribute. A name as Lean writes it never begins with `[`, so a value in the earlier form is never
taken for a list.

## Writing

The writers of images are unchanged: an image without a source is byte for byte what it was
(the gallery in `examples/` is compared with its files on every test run). The source is added to
a finished file:

* `withSourceSvg (svg : String) (s : Source)`, `withSourcePng`, `withSourceGif`,
  `withSourcePdf`, or `withSource`, which finds the format by the file's signature. Each returns
  `Except String ByteArray` (the SVG one a `String`), and fails if the file already has a
  source.
* For an SVG built from nodes, `Source.svgNodes` gives the three elements to put first among the
  children of `Svg.document`.

### SVG

Three elements, the first children of the root `<svg>` (after the root's own leading `title` and
`desc`, when it has them, so that its own title stays the picture's accessible name):

```xml
<title>Module.decl</title>
<desc>Generated by Module.decl in path/File.lean:59 with PILean 0.1.0</desc>
<metadata>
  <pilean:source xmlns:pilean="https://github.com/eric-vergo/PILean/ns/source/1"
      module=".." decl=".." file=".." line=".." column=".." repo=".." commit=".."
      version=".." fingerprint=".."/>
</metadata>
```

Absent optional fields are left out. Values are escaped with the writer's attribute escaping
(`&amp; &lt; &gt; &quot; &#39;`, tab, line feed and carriage return as character references).

### PNG and APNG

One `iTXt` chunk per field, uncompressed, UTF-8, with the keyword `PILean:` followed by the key
(`PILean:module`, `PILean:decl`, `PILean:file`, `PILean:line`, `PILean:column`, `PILean:repo`,
`PILean:commit`, `PILean:version`, `PILean:fingerprint`), directly after `IHDR`, so before `IDAT`
and, in an APNG, before `acTL` and every `fcTL`. The chunks have correct CRCs. The pixels and the
frames are not touched.

### GIF

One comment extension (`0x21 0xFE`) directly after the global colour table, so before the first
image and before any application extension. Its text is UTF-8 lines: `PILean source 1`, then
`key=value` for each field (the value is everything after the first `=`), each line ended by a line
feed, in sub-blocks of at most 255 bytes. A GIF comment is line based, so a value with a line
feed or a carriage return is refused (SVG and PNG carry them). The file must be a GIF89a file.

### PDF

The document information dictionary, added to the finished file by an incremental update
(ISO 32000-1, 7.5.6): after the file's `%%EOF` come one new object (numbered by the trailer's
`/Size`), a cross-reference section with that object alone, and a trailer with `/Size`, `/Root`,
`/Info` (the new object), `/Prev` (the earlier section) and `/ID` (the first string kept, the
second the first 16 bytes of the SHA-256 of the file and the new object), so the bytes of the
file before it are unchanged. The dictionary has one key per field, `/PILean:` followed by the key
(`/PILean:module`, `/PILean:decl`, …), each value a text string written as a hexadecimal string
of UTF-16BE with its byte order mark, and `/Title` (the declaration) and `/Producer`
(`PILean` and the version) beside them. The file must have a classic cross-reference table
(PILean's writer writes one), not a cross-reference stream.

## Reading

`Source.read? : ByteArray → Except String Source` finds the format by signature (PNG; `GIF8`;
`%PDF-`; otherwise UTF-8 text with an `<svg` tag) and treats everything as untrusted:

* The input must be at most 64 MiB (`maxInput`); each value at most 4096 bytes (`maxField`).
* Each key at most once (a repeat is an error); a value with a character XML 1.0 cannot carry is
  an error; unknown keys are ignored; the required keys
  must be there; `line` and `column` must be numbers; a fingerprint must have the form above.
* Nothing is executed or followed. A `repo` value is returned as text.
* SVG: a small bounded scanner over the bytes skips comments, processing instructions and CDATA
  sections, and reads only the attributes of the one `pilean:source` element, which must declare
  the namespace above (a second element, an unknown entity, a `<` in a value or a character
  reference to a character XML cannot carry is an error). The five XML entities and numeric
  character references are unescaped. There is no general XML parser.
* PNG and APNG: the chunks before the first `IDAT` are walked; the CRC of a source chunk must be
  right and it must be uncompressed. The image is not decoded.
* GIF: the extensions before the first image are walked; the comment that starts with
  `PILean source 1` is read; a larger one than 64 KiB, a second such comment or a carriage
  return in it is an error.
* PDF: the bounded reader of `PILean/Pdf/Read.lean` finds the last `startxref` in the last
  1024 bytes (followed by `%%EOF`), reads the cross-reference sections back through `/Prev` (at
  most 32, none twice, at most a million entries, sorted in `O(n log n)`), takes the newest
  trailer's `/Info` and parses that one object: nesting at most 32, strings at most 64 KiB,
  dictionaries at most 4096 keys, no key twice. Its keys `/PILean:…` must hold text strings
  (UTF-16BE with the byte order mark, no lone surrogate, or ASCII); other keys are ignored. No
  stream is decoded.
* What the readers accept is what the writers write: a value with a character XML cannot carry
  (NUL, say) is refused in every format, as the writers refuse it. One difference is kept on
  purpose: the APNG reader treats a frame delay with denominator 0 as a denominator of 100, as
  the APNG specification says; the writer never writes one.

### Links

`safeLink? : String → Option String` answers a URL only if it starts with `http://` or
`https://` (lowercase), has something after that, is at most 4096 bytes and has only printable
ASCII without `"`, `'`, `` ` ``, `<`, `>`, `\` and white space. Anything else (`javascript:`,
`data:`, `file:`, a non-ASCII character) gives `none`; a program that shows a link should use
only what this returns.

`escapeControl` writes control characters and the backslash of a string as escapes (`\n`, `\t`,
`\u{1b}`), for showing untrusted text on one line.

### Inert SVG

`Svg.isInert : String → Bool` answers whether an SVG document can be shown in a web page without
running script, loading anything from outside the document, or carrying event handlers;
`Svg.inertProblem?` gives the first reason it is not. It is a small bounded scan over the text,
not an XML parser, and it is strict: it accepts the SVG PILean writes (figures, graphs,
animations, and files with a source record) and refuses anything else that could be active.

* A document above 64 MiB is refused without being read; the work is linear in its size.
* The only markup is one `<?xml ...?>` declaration at the very start (with no `<` or `>`
  inside it), comments (without `--` inside, not starting with `>` or `->` and not ending with
  `-`, so that an HTML parser and an XML parser end them at the same place), and elements
  from a fixed list: `svg g path rect circle ellipse line polyline polygon text tspan title desc
  metadata pilean:source defs clipPath linearGradient radialGradient stop animate
  animateTransform set style`. `script`, `foreignObject`, `image`, `use`, `a`, any unknown
  element, a document type, an entity declaration, a CDATA section, any other processing
  instruction, and a tag or comment that is not closed are refused.
* Attribute names have ASCII letters, digits and `- _ : .` only, and values are quoted. Names
  starting with `on` (in any letter case) are refused, as are `style` attributes and `xml:base`.
  `href`, `xlink:href` and any name ending in `:href` are accepted only with a value that starts
  with `#`. A `url(` in a value must be followed by `#`. `javascript:` and `data:` are refused
  in any value, also with white space inside, as are the CSS image functions `image(`,
  `image-set(`, `cross-fade(` and `src(`. A backslash in a value is refused. An animation
  (`animate`, `set`, `animateTransform`) of `href`, a name ending in `:href`, or a name starting
  with `on` is refused (`attributeName` is recognised in any letter case, as an HTML parser
  reads it). An animation starts and ends on the clock only: its `begin` and `end` (in any letter
  case) must be lists, separated by `;`, of `indefinite` and clock values or offsets (an optional
  sign, digits, `:` and `.`, an optional unit `h`, `min`, `s` or `ms`); an event (`click`,
  `a.mouseover`, `accessKey(x)`), another element's timing (`a.end+1s`, `a.repeat(2)`) or the
  wall clock is refused, so no animation waits for the reader to do anything.
* Values are decoded before they are checked: the five XML entities and numeric character
  references are decoded, any other `&name;` is refused, so a reference cannot hide a word.
* The text of a `style` element may not contain `@import`, `@font-face`, `url(` that is not
  followed by `#`, `image(`, `image-set(`, `cross-fade(`, `src(`, `expression`, `binding`,
  `behavior`, `javascript:`, a backslash, a character reference, or any `<` other than the
  closing `</style>`. Text in other elements is not examined; a raw `<` always starts a tag.
* Elements are closed and nested properly, at most 256 deep; there is exactly one root element,
  `svg`, and nothing but white space and comments after it.

An SVG that passes can be placed in a page as an image or inline; the check says nothing about
whether the figure is the right one (see the fingerprint for that). Placed inline, the rules of
its `style` element apply to the whole page, as those of any inline SVG do: they cannot run
script or load anything, but they can restyle what is around the picture. The check is tested
against hand-written hostile documents; it is not proved, and no browser is part of the tests of
the core.

## `pilean-info`

```
lake exe pilean-info FILE
```

prints one `key: value` line per field, in the order of the table above, values with control
characters escaped. Exit status 0 on success; 1, with a message on standard error, if the file
cannot be read, is larger than 64 MiB, or has no valid source information; 2 on a wrong command
line. The function behind it is `PILean.Trust.infoLines`.

## Renderable figures

`PILean/Trust/Figure.lean`. A type with an instance of `ToOutputs` can be rendered to files:
`ToOutputs.outputs : α → Array Output`, each `Output` with a file-name suffix (`name`: `""`,
`"-dark"`, `"-poster"`), a `Format` (`svg`, `png`, `apng`, `gif`, `pdf`), the bytes (a function of
`Unit`, so nothing is computed before it is called; it can fail with a message) and `spec`, the
canonical encoding of what is drawn. An SVG output can also give the same picture as nodes for a
page that puts it inline (`inline`), and the problems the figure's checks report (`problems`;
see "Checks" below). The outputs of a motion also record the motion (`motion`) and its animated
SVG what a page needs to show it (`motionPage`; see "Motions" below).

| Type | Outputs |
|---|---|
| `Plot.Figure` | SVG; PNG; PDF |
| `Plane.Figure` | SVG; PNG; PDF; and, with a narrow width, SVG and PNG with the suffix `-narrow` |
| `Explorer` | the poster's SVG (with every frame for a page that shows them inline), PNG and PDF; then each frame `k` (from 0, in the order of `Explorer.frames`) as an SVG with the suffix `-frame-k`; at most `Explorer.maxFrames` frames and `Explorer.maxBytes` bytes of frames' SVG, or no output renders |
| `Graph` (default layered layout, light style, scale 1), or `GraphFigure` (graph, layout options, style, PNG scale) | SVG; PNG; PDF |
| `Animation` | animated SVG; APNG (file extension `png`); GIF; poster frame (PNG and PDF, suffix `-poster`) |
| `Plane.Motion`, `Plane.MotionPanels`, or `MotionFigure` (a motion, whether to write the APNG and GIF, frames a second) | animated SVG; the poster key's still (PNG and PDF, suffix `-poster`); the contact sheet (SVG, PNG and PDF, suffix `-keys`); each key `k`'s still (SVG and PNG, suffix `-key-k`); with a narrow rendition, the animated SVG and the stills with the suffix `-narrow`; the APNG and the GIF only with `MotionFigure.rasters` (see "Motions") |
| `Diagram.Diagram` | those of its plane figure (`Diagram.toPlane`) |

### Checks

A plot's labelling checks (`PILean.Plot.Check`) and a plane figure's layout checks
(`PILean.Plane.Check`) report problems at the level of the figure's `checks` field: as warnings,
which `pilean-build` prints and the Verso adapters report (the `problems` of the first SVG output
of the figure), or, at the level `fail`, as errors: every output of the figure fails, and
`pilean-build` exits with status 1. An explorer, and an animation made from plane figures
(`Plane.animation`, `Explorer.toAnimation`), carry the problems of their frames' figures, named by
frame, at the same levels.

### Inline pictures

A page may put a picture inline instead of linking its file. For every output whose `inline` is
a picture `i`, `i.document` (`Svg.document` of its size and nodes) is byte for byte the output's
bytes before the source record is added, and so exactly what the output's `spec` covers; this
holds for plots, plane figures (and their narrow renditions) and every frame of an explorer, and
the tests check it for every picture of the gallery. Each frame of an explorer is a file of its
own, with its manifest entry, SHA-256 and fingerprint, so a site check can compare every inline
`svg` element of a page with the file it was made from (after taking off what the page adds: the
theme `style` element, the id prefix, declaration links and the page's root attributes) and that
file with the manifest. The theme rules a page adds are keyed on the picture's light colours
(`InlineSvg.darkColours`), which the manifest entry records with the dark ones
(`ManifestEntry.darkColours`, `darkOpacities`, from `Output.theme`); a plane figure or a plot
whose colours that keying would get wrong is reported by its checks (`darkThemeClash`), and so is
every explorer frame drawn from one.

### The specification encoding

The specification of an output is the SVG document that PILean's deterministic writer
(`Svg.render`) makes from the figure's drawing, as UTF-8, before any source information is added:

* SVG outputs: the SVG document of the output itself, with text as `<text>` (as shapes when the
  text engine's strings are not plain text, such as LeAnTeX's, and, by default, for plane figures,
  `Plane.Figure.textAsShapes`).
* PNG and PDF outputs of a figure or a graph: the SVG document with text drawn as shapes, which
  is the drawing the PNG is rasterised from and the PDF is written from (the rasteriser and the
  PDF writer are not part of the specification; they are covered by the renderer's identity, see
  "The fingerprint"), so a figure's PNG and PDF share a fingerprint.
* An animation's APNG and GIF: the animated SVG document, which holds every frame; the poster
  (PNG and PDF): the SVG document of the poster frame.
* An explorer: the poster's SVG, PNG and PDF as for a figure; each frame's SVG, the SVG document
  of that frame.
* A motion: the animated SVG and, when written, the APNG and the GIF: the animated SVG document of
  the checked route; each key still and the poster: those of the key figure, as for a plane
  figure; the contact sheet as for a frame of an explorer.

The specification covers what is drawn: the sampled values of a function (the points the figure
takes), data, colours, sizes, text and layout. It does not cover the function's code, nor
anything that does not change the drawing. The declaration's source text is covered separately,
by the source hash.

### Motions

A motion of plane figures (`PILean.Plane.Motion`), or a picture of several motions as panels on
one clock (`PILean.Plane.MotionPanels`), is a figure of the build like any other
(`PILean/Trust/Motion.lean`). Its outputs read the motion checked once (`CheckedMotion`): a
checked motion is made only from the report of the motion's checks (`MotionReport.checked`,
`MotionPanelsReport.checked`; its constructor is private), so nothing can say it was checked
apart from the report. The animated SVG is the checked route's (`svg?`), never one of the routes
that end in `Unchecked`.

* **Check levels.** A motion's checks apply at its `checks` level. Under `fail` (the default) an
  error stops it. Under `warn` its errors are warnings on the animated SVG; under `ignore` they
  are not reported. In both, a move that misses its key is drawn as a crossfade, and the files
  are written. Whatever the level, a motion is stopped when it is not well formed (a caption per
  key, one step fewer than keys, the poster among the keys), when its written picture has an id
  twice (actor ids that differ but are written alike, such as `a b` and `a_b`), and, for a
  picture of panels, when its panels use different text engines. A stopped motion renders no
  file: every output fails with the messages of what stops it and has no inline picture, theme or
  page data, and `pilean-build` exits with status 1 having written nothing. A narrow rendition is
  also stopped by its own errors under `fail`.
* **What is recorded.** Every file of a motion has its own manifest entry with SHA-256 and
  fingerprint, and records the motion, in its source record (the key `motion`) and in its
  manifest entry (the keys `kind` … `unchecked`), which `pilean-verify` compares: the number of
  key frames, the length of the cycle in seconds, exactly, the number of captions, the check
  level (`fail`, `warn`, `ignore`), and whether errors were left (`unchecked`). Reading the
  manifest also requires that the files of a motion list exactly the key stills it counts
  (`motionKeyProblem?`). Its standing is recorded as for any figure.
* **Strict builds.** `pilean-build --require-checked` refuses, before rendering anything, every
  motion not built at `fail` without errors left. A site that publishes motions should build with
  `--require-standing --require-checked`.
* **Inline in a page.** The animated SVG's output carries `MotionData` (`Output.motionPage`): the
  record; the moving picture without the file's `title`, `desc`, reduced-motion `style` element
  and poster group (`live`, with the theme's colour pairs, which the manifest records as for any
  inline picture), so that a page's own rules decide what is shown under reduced motion; the
  stills with their captions and the poster (`stills`, a `FrameSet` whose picture `k` is the file
  `-key-k`'s picture); and the table of the steps (`MotionStepRow`: per step its duration, whether
  it is idle, and each move with its panel, actor, kind, centre and exact fraction of a turn or
  vector, and what the animation draws for it: the move, or `crossfade` when it does not land).
  The file's root holds, in order, the title and description, that `style` element, the nodes of
  `live`, and the poster group, so a site check can rebuild the file from what the page shows; the
  tests check this for every golden motion.
* **What a page may say.** The standing ("Illustration." or the linked theorem), then
  `MotionData.words`: "An animation drawn from N key frames; the stills are the key figures as
  drawn.", then what the browser does between key frames, built from the moves the animation
  draws (`MotionData.betweenWords`: it turns drawn items about the stated centres, slides them
  along the stated vectors, fades items in or out, changes the outlines of drawn items,
  crossfades items that change without a declared move, or nothing moves), and, for a motion not
  checked strictly (`MotionData.unchecked`, which a page must show), what that means
  (`MotionData.checkWords`). Whether the key figures' data is exact is the author's to say, in the
  figure's description: a key may be drawn from floating-point data. The step table goes with it.
  A motion is marked `@[figure illustration]` unless a theorem is linked to it; `figure_links`
  works for a motion as for any figure, and its rule is the same: the theorem's statement names
  the motion's constant. What a theorem about a motion can state is its key figures and its
  declared moves (`motionLinkedWords`); the frames the browser draws between the keys are not
  part of any statement.
* **What is verified, at each level.** At every level: each still is, byte for byte, the key as
  drawn (the plane figure `Motion.keyFigure k` as the plane figures' pipeline draws it; the
  picture's key `MotionPanelsReport.keyStillSvg k` and `keyStillPng k`), and the record says the
  level and whether errors were left. At `fail` with no error left: each declared turn or slide
  carries its actor onto the next key (within 0.01 px), the whole baked drawing is within 0.05 px
  of the still at every rest, and the written SVG read back agrees with the baked drawing
  (`Motion.problems`; for panels, the same for every panel and for the composed picture). At
  `warn` or `ignore` with errors left, none of that holds for the steps the errors name: the
  record says `unchecked`, the step table marks each move drawn as a crossfade, and the page must
  say so. The browser's drawing between the keys is not part of the build at any level:
  `tools/motion-browser-check.py` measures it in Chromium, outside `lake test`. An illustration
  carries no theorem, and a linked theorem says what its statement says.
* **Accessible names.** The animated SVG's own `title` (the motion's title) is the first `title`
  child of the root; the build writes the source record after it and the `desc`, so the record's
  title (the declaration's name) does not become the picture's accessible name. The contact
  sheet's SVG, whose text is drawn as shapes, has a `title` and a `desc` listing the captions.
* **Inertness.** Every SVG a build writes passes `Svg.isInert` (the build refuses one that does
  not, and `pilean-verify` reports one as `not inert`); a motion's animations start on the clock
  (`begin="0s"`), and an animation started or ended by an event or by another element's timing is
  refused.

## The attribute `figure` and `figures%`

`PILean/Trust/Attr.lean` (the only part of PILean that imports `Lean`; the library proper does
not). `@[figure]` on a definition whose type has a `ToOutputs` instance (it is an error
otherwise, and for a private declaration) records in an environment extension, which is exported
with the module:

* the module, the declaration's name, and the file (the module's name with `/` for `.` and
  `.lean`: `PILeanTest/Examples.lean`; never an absolute path);
* the line (from 1) and column where the declaration starts, taken from the range Lean stores for
  it: the start of its doc comment when it has one;
* the SHA-256 (hexadecimal) of the declaration's source text, the text of that range, taken from
  the file being elaborated.

Lean stores the range only after the attributes are applied, so the attribute adds a command
elaborator for declarations and `attribute` commands that mention `figure`, which elaborates the
command as usual and then records its figures.

The term `figures%` becomes, where it is used, an `Array FigureEntry`: one entry for every
registered declaration of the environment (imported modules included, and the declarations above
it in the same module), sorted by module and then declaration name, each holding the recorded
data and `fun _ => ToOutputs.outputs decl`.

The command `figure_links fig thm` links a theorem to a registered figure. It is an error, so
the module does not build, unless `thm` is a theorem, depends on no `sorry` and on no axiom other
than `propext`, `Classical.choice` and `Quot.sound`, and its statement names the figure itself.
The links are kept in an environment extension (`figureTheorems`).

The rule, exactly (`statementNamesFigure`, with `ruleStatement`):

1. The statement of `thm` is taken as Lean elaborates it and reduced, everywhere in the term and
   until nothing is left to reduce, by three steps and no others: a `let` or `have` is replaced
   by its body with the value put for the variable; `letFun v f` (the form `have` took in
   earlier versions of Lean) becomes `f v`; an application of a `fun` to arguments is
   beta-reduced. A declared statement has no metavariables, so none are instantiated.
   Eta-reduction is not applied: it removes a binder and a variable, never a constant, so it
   could not change the outcome. A statement whose reduction runs past Lean's limits
   (heartbeats, recursion depth) is refused with Lean's error.
2. The constant `fig` must occur in the result.

Where `thm` is declared is not part of the rule. It is usually the figure's module. In the
Mathlib package it is a module that imports the figure's: the figure's module imports nothing
from Mathlib, so that the program that draws it does not contain Mathlib, and the theorem needs
Mathlib.

What this means:

* A field of the figure is a projection applied to it, so a statement about `fig.panels`,
  `fig.edges`, `fig.nodes` or `fig.frameSeq` names the figure. The usual shape begins with an
  equation that says what the figure holds, `fig.panels.map (·.series) = #[#[s₁, s₂]]` or
  `fig = builder data`, and goes on about `s₁` and `s₂`, or about `data`.
* No definition is unfolded. A statement about a definition the figure is built from (a series, a
  data list, a relation), or about a term that happens to equal the figure, does not name it and
  is refused: the figure could be changed and leave such a statement true.
* A name that occurs only in the value of a `let` the statement does not use, or only as the
  argument of a `fun` that discards it (`(fun _ => P) fig`, also when the `fun` is passed
  through other `fun`s first), does not count: the reduction removes it.
* The reduction stops at definitions, so a name that a definition would discard still counts.
  These are accepted although the figure plays no part in what they say, and the rule does not
  try to see through them: a `match` on the figure (`match fig with | _ => P`), a projection of
  a structure or pair built around it (`(fig, P).2`), a definition that ignores an argument or
  passes a `fun` on (`Function.const _ P fig`, `id (fun _ => P) fig`, or one of the author's
  own), a recursor whose unused case holds the figure (`Nat.rec P (fun _ _ => fig = fig) 0`),
  and an `if` whose condition settles the branch.
* The rule is about names; it does not judge what the statement says. A statement that names
  the figure and says nothing of substance about it passes: `fig = fig`, the figure in a
  hypothesis that is never used or in a branch that is never taken, a property that holds of
  every figure, and the shapes of the previous item. What the theorem says is for its reader to
  judge (`docs/PROOFS.md`).

A link is a pointer from a picture to a statement to read, not a certificate that the picture is
correct.

## Standing

A figure is *linked* or an *illustration* (`PILean.Trust.Standing`). It is linked when at least
one theorem is linked to it by `figure_links` and that link passes the rule of `figure_links`
again where the build's table of figures (`figures%`) is elaborated (`figureStanding`); it is then
recorded with the names of those theorems. Otherwise it is an illustration: a figure to which no
theorem is linked. `@[figure illustration]` marks a figure as one openly, and `figure_links`
refuses a figure so marked. `figure_proves` is another name for the command `figure_links`.

* `figures%` sets the standing on every output of a figure (`Output.standing`;
  `FigureEntry.standing` reads it), so a build writes it into every file's source record
  (`standing`, `theorems`) and into the manifest (the keys `standing` and `theorems`), and
  `pilean-info` prints it. It is not part of the fingerprint, which
  identifies the drawing and the declaration; it is part of the file, so the file's SHA-256 in the
  manifest covers it. The readers also take the records and manifests of the earlier writers:
  manifests of the format `pilean-manifest-3`, before motions, those of the format
  `pilean-manifest-2`, whose `theorems` is one string of names separated by single spaces, and of the format `pilean-manifest-1` and records that wrote the standing
  `proved` and the key `proves`: `proved` reads as `linked` and `proves` as `theorems`
  (`readStanding`).
* `pilean-build --require-standing` (with or without `--check`) fails, before rendering anything,
  if a figure is an illustration without the marking, naming each such figure: a project can
  require that every picture either has a linked theorem or is openly marked.
* `pilean-verify` compares the recorded standing and theorems of each file with the manifest, and
  ends each `ok` line with the standing the file records (` [recorded: linked to T]`,
  ` [recorded: illustration]`). It checks no theorem: what it prints is what the file and the
  manifest say.
* What `linked` establishes is the rule of `figure_links`: a theorem free of `sorry` and of
  non-standard axioms whose statement names the figure. It says nothing about what the statement
  says; that is for its reader (`docs/PROOFS.md`). A figure whose theorem is in a module the
  build's driver does not import is an illustration to that build.
* The Verso adapters build their own table of figures (`site_figures%`), which sets the standing
  as `figures%` does. Each figure of a site has a page that states it: "Linked theorem: T" with
  T's statement and axioms and the sentence below on what PILean checked, or "Illustration: no
  theorem is linked to it". The site's build fails when a caption names a theorem (`links :=`, or
  `proves :=`, the same option) that the standing does not record, and when a page's standing
  differs from the files the build wrote.

A figure's page says of each linked theorem T:

PILean checked that T is proved from the standard axioms and that its statement names this
figure; it did not check what T says.

What a linked theorem says is in its statement. The theorems of this library state the figure's
data and, where written, its colour roles, texts and title; none says how text is rendered, which
colour values a style gives, or how the exact numbers become pixels.

## The fingerprint

`PILean/Trust/Fingerprint.lean`. `fingerprint spec src` is the lowercase hexadecimal SHA-256 of
this byte string:

1. the header `PILean fingerprint 2` and a line feed;
2. nine fields in this order: module, declaration, file, line, column, library version
   (`PILean.version`), renderer (`rendererWith` of the output's text engine), source-text hash,
   specification;
3. each field as its length in bytes (a 64-bit unsigned number, big-endian) followed by its
   bytes; the text fields are UTF-8, the line and the column are decimal digits, the source-text
   hash is its 64 hexadecimal digits.

The renderer, `PILean.Trust.rendererId` (`PILean/Trust/Renderer.lean`), is the SHA-256 of the
Lean toolchain's version and of the source files of every library module that turns a figure into
bytes (the plots, plane figures, graphs and animations, the motions of plane figures and their
outputs, the SVG writer, the rasteriser, the lettering, the PNG, APNG, GIF and PDF writers, the
source records: the modules `Renderer.lean` imports, listed in `rendererSources`). It is computed from the files' text as it was when the library was compiled
(`include_str`), so nobody has to remember to change it: any change to that code changes every fingerprint, even a
change to a comment, and a change to the rasteriser that leaves the SVG specification alone
still changes the fingerprints of the PNG files. The tests check that the list is exactly the
modules `Renderer.lean` imports and that each text is the file's current content.

An output drawn with a text engine other than the built-in lettering records that engine's
identity (`Output.textEngine`, from `TextEngine.id`), and its renderer field is
`rendererWith id`: the SHA-256 of `rendererId`, a line feed and the identity (for the lettering,
whose code `rendererId` already covers, it is `rendererId` itself). The LeAnTeX engine's identity
names the LeAnTeX commit and the SHA-256 of every font file it reads (`leantex/README.md`), so
the fingerprint changes with either.

The file's `Source` record carries this fingerprint, so changing the specification, the source
text, the position, the library version or the renderer changes it. The repository and the commit are not part
of it (the same figure built at two commits has the same fingerprint if neither its drawing nor
its declaration changed, apart from the line). Output formats of one animation share one
fingerprint, because they share the specification; the SHA-256 of each file is in the manifest.

## `pilean-build`

A project's driver is three lines:

```lean
import MyFigures
import PILean.Trust.Build
def main (args : List String) : IO UInt32 := PILean.Trust.buildMain figures% args
```

(with `lean_exe` in the project's lakefile). PILean's own driver is `lake exe pilean-build`; it
renders the gallery figures that carry `@[figure]`.

```
pilean-build [--out DIR] [--repo URL] [--commit SHA] [--check] [--require-standing]
             [--require-checked]
```

* Without `--check`, every output of every entry is rendered, the source record (with the
  fingerprint, and `--repo` and `--commit` if given) is written into it, and the file is written
  to `DIR/<module with / for .>/<declaration without the module prefix><suffix>.<extension>`
  (`--out` defaults to `figures`), then `DIR/manifest.json`. The output is deterministic: the
  same entries, options and library give the same bytes. Nothing is written if any figure fails
  to render. File names have only `[A-Za-z0-9._-]` (every other character becomes `_`); an empty
  component, `.` or `..` in a path is refused, so nothing is written outside `DIR`.
* `--require-checked` (with or without `--check`) fails, before rendering anything, if a motion
  was not built at the check level `fail` without errors left, naming each ("Motions").
* `--repo` must be an `http` or `https` link (`safeLink?`), `--commit` 4 to 64 lowercase
  hexadecimal digits.
* With `--check`, the output is rendered in memory and compared byte for byte with `DIR` (give the
  same `--repo` and `--commit` as the build). It prints `stale: PATH` (different bytes, the manifest
  included), `missing: PATH`, and `extra: PATH` (a file under `DIR` that is neither in the manifest
  nor the manifest itself), and `ok: N files match` if all is well. The folder is listed to at most
  32 levels of directories and 100,000 entries (directories count, empty ones included); a folder
  beyond either bound is not listed partly: it gets the line `cannot check: REASON` and fails.
* Exit status 0 on success, 1 if a file is stale, missing or extra, the folder cannot be listed
  completely or a figure cannot be rendered, 2 on a wrong command line.
* Bounds: at most 4096 figures and 65,536 files (the most a manifest may list), each file at
  most 64 MiB with its source record in (the most the source reader of `pilean-verify` reads),
  checked on the finished file; a file whose bytes are not of its output's format (an `apng`
  output must have an `acTL` chunk before its image data, a `png` output none, a `pdf` output
  starts with `%PDF-`) is refused, and so is an SVG that is not inert (`Svg.inertProblem?`, "Inert
  SVG") and a PDF that fails the structural check (`Pdf.check`, `PILean/Pdf/Check.lean`). So every
  file a build writes is one `pilean-verify` can check.

### The manifest

`DIR/manifest.json` is one JSON object, `{"format":"pilean-manifest-4","files":[ ... ]}`, with one
line for each output, sorted by `path`, every object with the keys in this order:

| Key | Meaning |
|---|---|
| `path` | the file below `DIR`, `/` as separator |
| `format` | `svg`, `png`, `apng`, `gif` or `pdf` |
| `bytes` | the size of the file |
| `sha256` | the SHA-256 of the file's bytes |
| `fingerprint` | the fingerprint recorded in the file |
| `module`, `decl`, `file`, `line`, `column`, `version` | the source record |
| `repo`, `commit` | only if the build was given them |
| `darkColours`, `darkOpacities` | for a file a page can put inline: the theme's colour pairs |
| `standing`, `theorems` | the standing recorded in the file, and its theorems as a JSON array of strings ("Standing"; a manifest of the format `pilean-manifest-2` has one string of names separated by single spaces, and one of the format `pilean-manifest-1` has it under `proves`, read as `theorems`; `Manifest.parse` reads all of them and refuses an array in those two formats and a string in the later ones) |
| `kind`, `keys`, `cycle`, `captions`, `checks`, `unchecked` | only for a file of a motion, the record its source record holds: `kind` is `motion`, `keys` the number of key frames (at least one), `cycle` the length of one cycle in seconds, exactly, as a string `n` or `n/d` in lowest terms, `captions` the number of captions, `checks` the level (`fail`, `warn`, `ignore`), `unchecked` a boolean, whether errors were left ("Motions") |

`Manifest.parse` refuses an entry of this format with a key the table does not have, a `kind`
other than `motion`, the keys of a motion without `kind` or `kind` without them, a cycle or a level
written otherwise, a manifest in which the files of one declaration do not all record the same
motion (or all none), and one in which the files of a motion do not list exactly the key stills
it counts (the SVG and the PNG `-key-k` for each key, at each width). It reads the format before motions, `pilean-manifest-3`, as before (its other keys
ignored, no motion), and the earlier ones; a reader of an earlier format refuses this one by its
`format`, so no older reader takes a motion's files for those of another figure.

Strings are escaped as in JSON (`\"`, `\\`, `\n`, `\r`, `\t`, `\u00XX` for other control
characters).

## `pilean-verify`

```
lake exe pilean-verify DIR
```

resolves `DIR` once and reads `DIR/manifest.json` as untrusted input: a regular file (not a symbolic
link, not a FIFO or device; checked before it is opened), at most 16 MiB, read by a small bounded
JSON reader (`PILean/Trust/Json.lean`: nesting at most 8, strings at most 64 KiB, integers of at
most 15 digits only, no repeated key, nothing after the value). The manifest is rejected as a whole,
before any file is touched, if a path is empty, longer than 1024 bytes, absolute, has `..` or `.` or
an empty component, a backslash, a colon or any character outside `[A-Za-z0-9._/-]`, if a path is
listed twice, a format is unknown or a hash is not 64 lowercase hexadecimal digits. The folder is
then listed, to at most 32 levels of directories and 100,000 entries (directories count, empty ones
included); a folder beyond either bound is an error (exit status 1, a message, no line about any
file), never a partial listing. Then each listed file gets one line, and after them each file that
is not listed:

| Line | Meaning |
|---|---|
| `ok: PATH` | a regular file of the listed size and SHA-256 and of the listed format, inert if it is an SVG, whose source record agrees with the manifest (module, declaration, file, line, column, version, repository, commit, fingerprint, standing, theorems and the record of a motion); the line ends with the recorded standing, if any |
| `missing: PATH` | no file has that path, spelled exactly so (on a file system that ignores case, a file found only under another spelling is `missing`, and listed as `extra` under its own) |
| `changed: PATH` | another size or hash |
| `format differs: PATH` | the bytes are not of the listed format (`svg`, `png`, `apng` with an `acTL` chunk before the image data, `gif`, `pdf`) |
| `not inert: PATH` | an SVG file that is not inert (`Svg.inertProblem?`), which no build writes |
| `not a regular file: PATH` | the file, or a directory on its way below `DIR`, is a symbolic link, a directory, a FIFO or a device (nothing is followed or opened) |
| `source differs: PATH` | the source record in the file differs from the manifest |
| `no source: PATH` | the file has no readable source record |
| `extra: PATH` | a file below `DIR` that the manifest does not list (other than the manifest; a symbolic link counts as a file and is not followed) |

Every path and message printed comes from the folder and goes through `escapeControl`, so no
line can be forged or hidden by the manifest. Exit status 0 only if every line is `ok`; 1
otherwise, or if the manifest is missing or invalid; 2
on a wrong command line. `pilean-verify` does not render anything: it checks that the directory
is what its manifest says. `pilean-build --check` checks that it is what the build produces now.

### What the answers establish

* `pilean-info` prints what a file says about itself. A source record is written by whoever
  wrote the file; nothing is signed, so the record alone establishes nothing.
* `pilean-verify` exiting 0 establishes that the directory and its manifest agree: every listed file
  is there under exactly its listed name, with the listed size, SHA-256 and format, is inert if it
  is an SVG, and carries the listed source record, and there is no other file (a folder too deep or too large to list
  completely is an error, not a pass; directories that hold no file are not compared). It does not
  establish where either came from. Someone who can write both the files and the manifest can make a
  directory that passes, with any source record; the fingerprint is compared with the manifest's,
  not recomputed.
* `pilean-build --check` exiting 0 establishes that the directory holds, byte for byte, what
  the driver that was run renders now from the declarations compiled into it, and nothing else.
  That ties the files to the Lean source to the extent that the driver was built from that
  source by a toolchain you trust, on the checkout you mean. It is the only one of the three
  that looks at the Lean declarations.
* None of them says that a picture is correct: the fingerprint identifies a drawing and its
  declaration, and the theorems (`docs/PROOFS.md`) are about the Lean object, not the pixels.
* The file checks are made with `lstat` before each open; a folder that another process changes
  during the check is outside what they defend against (`PILean/Trust/Files.lean`).

### Pictures put inline in a page

A Verso page can put a figure's picture inline (`inline := true`, and every frame of an
explorer) instead of an `<img>` of its file. Such a picture is still a file of the figures
folder: every inline picture is the body of an SVG output, listed in the manifest with its
fingerprint like any other (an explorer's frame `k` is the output `-frame-k`), and the page's
`svg` element names that file (`data-pilean-file`). What the page adds to the file's picture is
fixed: a `style` element of class `pilean-theme` (the dark theme's colours), a prefix on every
id and reference to an id, a link around each element that names a declaration, and the root's
page attributes (class, id, role, accessible name, the view box the script starts from); the
file's source record is not in the page. The manifest entry of a file a page can put inline
records the theme's data: its light colours paired with the dark ones (`darkColours`) and its
tint opacities likewise (`darkOpacities`), from the figure's style. The example's site check
(`verso/example/tests/inline_check.py`) requires the page's `pilean-theme` element to be,
character for character, the rules the adapter derives from those recorded pairs and the
picture's id, and the picture to have no other `style` element; it takes the page's additions
away and compares the page's picture with the file element for element and attribute for
attribute, and the file's SHA-256 with the manifest; a page whose picture or theme rules differ,
that names no file, or names one the manifest does not list fails it. The site check
ties a page's picture to its file and the page's theme rules to the pairs recorded in the
manifest. The manifest's pairs are tied to the source only by `--check-figures`, which rebuilds
the figures and reports a stale manifest; `pilean-verify` alone does not catch a page and a
manifest edited together. The rest of the page (its own CSS, its other elements, an `svg` without
the class `pilean-inline-svg`) is not covered. Like the rest of this page, it establishes
agreement between the page, the files and the manifest, not where they came from.

## Use in CI

Figures are never committed by hand. Either of two set-ups:

1. **Build into the site.** CI runs the project's build driver and the site uses the folder:
   `lake exe my-figures --out site/figures --repo URL --commit "$COMMIT"`. Nothing under
   `site/figures` is in version control.
2. **Keep them committed and prove them.** The folder is in version control, written by
   the driver only, and CI runs `--check` with the same `--repo` and `--commit` (or none, if
   the committed files were built without), which fails when a committed file is not what the
   build produces (edited by hand, outdated, missing, or left over).

A workflow as plain shell steps:

```sh
lake build
lake exe my-figures --out site/figures --repo "$REPO_URL" --commit "$(git rev-parse HEAD)"
lake exe pilean-verify site/figures        # the folder agrees with its manifest
# keeping the folder in version control instead:
lake exe my-figures --out figures --check   # fails on any stale, missing or extra file
```

A change to a figure's declaration changes its source hash and so its fingerprint, and a change to
a sampled value or to the drawing changes the specification; either way `--check` reports the files
as stale until the build writes them again.
